# ADR-019: Multi-product platform architecture (one company, many services)

**Date:** 2026-09-26. **Status:** Accepted (owner request of 2026-09-26); delivered in steps by the [DevOps roadmap](../../10-devops/devops-roadmap.md#multi-product-architecture-track). Builds on ADR-008 (platform and product planes), ADR-011 (one account), and ADR-018 (Kubernetes delivery). As Oxinov adds products (Edu now; Market, Jobs, Services next), every product must be independently releasable, isolated in failure, cost, and data, and cheap to add.

1. **One Helm release and namespace per plane.** A `platform` release (Keycloak, PostgreSQL, mail relay, account portal, platform API) and one release per product (`edu`, later `market`, …), each in its own Kubernetes namespace with resource quotas and network policies, all from the shared chart. A failed release rolls back only its own product, and products release on their own schedule.
2. **One service catalog.** `services.yaml` at the repository root is the single source of truth for every service: product, image and build target, build inputs, port, host, owner, and resource size. The release planner, CI, the chart values, and the documentation read it; `oxctl new-service <product> <name>` scaffolds the folders and the catalog entry (golden path). No service is registered by hand in several places. *Implemented 2026-09-26: see the [service catalog](../../08-engineering/service-catalog.md); `oxctl new-service` scaffolds services.*
3. **Events between products, not direct calls.** Services write events to an outbox table in their own database in the same transaction, and a relay publishes them to Amazon SNS topics with an SQS queue per consumer (at-least-once, idempotent consumers, dead-letter queues). First events: `account.created`, `entitlement.changed`, `tenant.member.joined`. Synchronous calls stay for queries that need an immediate answer, through versioned APIs only.
4. **Feature flags.** Server-side flags per tenant, plan, or percentage, stored in the platform database behind the OpenFeature API so a hosted provider can replace it later. Deploying code (every push, NFR-17) is separate from releasing a feature; flags are removed once a feature is fully on.
5. **Shared observability.** OpenTelemetry tracing and metrics added once to `@oxinov/server-kit` and the web apps, propagating a trace ID across portal, APIs, and sign-in; one dashboard, service level, and error-rate alert per product.
6. **Contracts and ownership.** Versioned OpenAPI per API with a backward-compatibility check in CI and generated clients; `CODEOWNERS` per service; a written service level per product.
7. **Cost and data isolation.** Cost-allocation tags per product on AWS resources and namespaces, reported monthly. Each product keeps its own database and role today; regulated products (Market escrow and KYC) get their own database instance and, when they launch, their own AWS account.
8. **Modular monolith per product.** Each product stays one API until a measured scaling, security, or ownership need justifies extracting a service (YAGNI).

Consequences: more releases and namespaces to operate (automated by the catalog and scripts); events add eventual consistency and need idempotent handlers; a small amount of platform work lands before the second product. Alternatives considered: one release for everything (simplest, but one bad change rolls back the whole company), a service mesh (too heavy for one node), and a message broker such as Kafka or RabbitMQ (always-on cost and operations; SNS/SQS costs cents at this scale).
