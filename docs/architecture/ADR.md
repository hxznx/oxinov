# Architecture decision records

Record each decision with date, status, context, choice, consequences, and alternatives considered. Do not silently change the stack in the FRD.

## ADR-001: PostgreSQL as system of record

**Date:** 2026-09-24. **Status:** Accepted. Use PostgreSQL for transactional platform and LMS data. PostgreSQL runs in Docker for local development and CI; production uses Amazon RDS for PostgreSQL with encryption, backups, isolated data subnets, and Multi-AZ according to the environment availability target. Default to shared tenant-scoped LMS tables with RLS and API authorization; offer a dedicated database only for a justified customer tier. Redis and object storage are supporting systems.

## ADR-002: Separate frontend and backend

**Status:** Proposed. Next.js renders web UI; NestJS owns APIs and business rules used by web and mobile. Separate Docker targets support independent builds and scaling.

## ADR-003: One shared mobile app

**Status:** Proposed. A single Expo app lets users switch their tenant workspaces and renders tenant branding. Separately branded binaries require a future decision because they multiply store releases.

## ADR-004: Prometheus and Grafana observability baseline

**Date:** 2026-09-23. **Status:** Accepted for the initial implementation. Services expose Prometheus-compatible metrics only on the private network. Prometheus stores short-term metrics and evaluates version-controlled rules; Alertmanager routes alerts; Grafana loads data sources and dashboards from version-controlled provisioning files. PostgreSQL and Redis use dedicated exporters. Do not use tenant IDs, user IDs, email addresses, URLs with identifiers, or other unbounded values as metric labels. Production may replace these containers with compatible managed services while preserving metric names, dashboards, and alert behavior.

## ADR-005: Separate security operations pipeline

**Date:** 2026-09-24. **Status:** Accepted as the baseline design. Operational metrics remain in Prometheus/Grafana. Security events follow the versioned schema under `security/soc/` and are sent to an access-controlled SIEM. OpenSearch Security Analytics with portable Sigma rules is the initial SIEM recommendation; a compatible managed SIEM may replace it. Amazon GuardDuty Runtime Monitoring supplies initial ECS Fargate runtime detections. Falco or GuardDuty may cover later EKS/EC2 workloads. Wazuh is optional when endpoint/host agents, file-integrity monitoring, inventory, or compliance capabilities justify the additional platform. Actual incident evidence is never stored in Git.

## ADR-006: Tenant context through transaction-local settings and a non-bypass role

**Date:** 2026-09-24. **Status:** Accepted for the first backend slice. The API connects as `oxinov_app` (no superuser, no `BYPASSRLS`, no DDL, no delete on audit history). Every data operation runs inside one transaction that first calls `set_config('app.tenant_id' | 'app.user_id' | 'app.auth_subject', value, true)`; row-level security policies compare rows to those settings and match nothing when they are absent. Tenant-owned tables also use composite `(tenant_id, id)` foreign keys so cross-tenant references are rejected by constraints. Consequences: every query needs a short transaction (acceptable at current scale; revisit with PgBouncer transaction pooling, which is compatible), and each new table must add its policy and grants in the same migration. Alternatives considered: per-request `SET ROLE` per tenant (role explosion), schema-per-tenant (migration fan-out), application checks only (single point of failure).

## ADR-007: Identity token verification and local development tokens

**Date:** 2026-09-24. **Status:** Accepted. The API verifies bearer tokens against an approved OIDC provider's JWKS (`AUTH_ISSUER`, `AUTH_JWKS_URL`, optional `AUTH_AUDIENCE`) without depending on a provider SDK. Only the subject, `email`, and `email_verified` claims are used by the current LMS slice; tenant roles always come from PostgreSQL. The provider client must supply the required verified-email claims before tenant creation can succeed. For local work and tests, HS256 tokens with issuer `oxinov-dev` are accepted when `AUTH_DEV_JWT_SECRET` is set; configuration refuses that secret unless `DEPLOY_ENVIRONMENT` is `local` or `ci` (amended 2026-09-24 after review: staging was previously allowed). Staging and production also require `AUTH_AUDIENCE`, so a token issued for another Oxinov product is rejected (FR-ID-2207).

## ADR-008: Shared company control plane with independent product planes

**Date:** 2026-09-24. **Status:** Accepted as the target architecture. `oxinov.com` provides the public company presence, `app.oxinov.com` provides one account and product launcher, and an OIDC identity service provides single sign on. The control plane owns organizations, product catalogue, plans, entitlements, shared billing records, audit, privacy, and support access. Oxinov Edu and every later product own their product workflows, deployments, and data and integrate through versioned APIs and events. Begin with modular applications and a transactional outbox; extract services or introduce a message platform only for measured scale, availability, security, data, or team-ownership needs. Keycloak is the default OIDC implementation while the application contract remains provider-neutral. Existing Oxinov Edu code is migrated incrementally rather than rewritten.

## ADR-009: AWS as the production cloud

**Date:** 2026-09-24. **Status:** Accepted. AWS is the production cloud, with `ap-south-1` Mumbai as the primary region subject to pre-launch Nepal network latency verification. Use separate accounts and VPCs for production and non-production, at least two Availability Zones for production, CloudFront/WAF and an Application Load Balancer at the public edge, ECS Fargate for initial Docker workloads, RDS PostgreSQL, ElastiCache, S3, ECR, Route 53, Secrets Manager/KMS, and Terraform. Store encrypted recovery copies in `ap-south-2` Hyderabad initially; add warm or active multi-region compute only when recovery objectives justify its cost. Amazon EKS remains a later option based on measured scale or team ownership. Alternatives considered were Google Cloud Delhi/Mumbai, which may offer strong Nepal latency, and Azure; AWS was selected for the overall networking, managed-service, security, and container ecosystem required by the product portfolio.

## ADR-010: Adopt Flo Softwares marketplace concepts as Oxinov product planes

**Date:** 2026-09-24. **Status:** Accepted in principle; each product remains subject to its release gate. The Flo Softwares organization contains three marketplace concepts: an agricultural commodity marketplace (KrishiConnect / BT-Bazz Commodity Market), an HR and jobs platform, and the Kaji service marketplace, plus a BT-Bazz OIDC authentication concept. They become three Oxinov product planes: Oxinov Commodity Market (`market.oxinov.com`, originally drafted as Oxinov Agri Market; see ADR-013), Oxinov Jobs (`jobs.oxinov.com`), and Oxinov Services Market (`services.oxinov.com`), each with a charter under `docs/products/`.

Choice: rebuild each product on the Oxinov stack (Next.js, NestJS, PostgreSQL with Prisma and row-level security, shared OIDC) rather than importing the Express applications. Source repositories are reference material for requirements, data models, screens, and business rules. Capabilities duplicated across the three concepts move to shared owners: identity, OTP, sessions, KYC, payments ledger, notifications, messaging, and file storage to the platform control plane; training, courses, exams, and certifications to Oxinov Edu. The BT-Bazz OIDC concept informs the Keycloak client and per-product role configuration but does not replace the ADR-008 identity decision.

Preconditions: Oxinov Pvt. Ltd. holds written rights to the Flo Softwares code, designs, and product names, including contributions by other developers; secrets committed to the source repositories are rotated before any content is reused; no stored-value wallet or customer-fund holding is built without Nepal Rastra Bank licensing review.

Consequences: the platform foundation must deliver shared KYC and payments before any of the three products launches, and the products are delivered one at a time in the order Oxinov Commodity Market, Jobs, Services Market. Alternatives considered: running the existing Express applications behind the Oxinov domain (rejected: four separate logins, duplicated KYC and payments, no tenant isolation, and inconsistent security and observability), and keeping the products under a separate Flo Softwares brand (rejected: fragments the Oxinov identity and customer account).

## ADR-011: One Oxinov account with simple sign-in and progressive trust

**Date:** 2026-09-24. **Status:** Accepted. Customers sign in at `id.oxinov.com` with Continue with Google or an email one-time code; Continue with Apple is added before an iOS app ships; customer passwords are not offered. One Oxinov account works across every launched product through OIDC single sign-on, and first sign-in grants a free member entitlement to all launched products. Sign-in stays low-friction by deferring checks: a verified phone (T2), individual KYC (T3), or business KYC (T4), plus just-in-time acceptance of a product-role policy, are required only for actions that affect other people or move money. The platform control plane owns trust levels, policy acceptances, and KYC; products enforce the required level per action. Staff use separate identities with mandatory MFA. Details are in [identity and access](IDENTITY-AND-ACCESS.md) and [platform policies](../company/PLATFORM-POLICIES.md).

Consequences: the platform needs SMS verification, KYC review, and policy-version storage before any marketplace launches; Keycloak must be configured with Google brokering, verified-email-only linking, and an email one-time-code flow (an extension, if required, needs review under the dependency policy). This refines ADR-008: "explicit entitlements" remain, but the member entitlement is granted automatically. Alternatives considered: per-product sign-up (rejected: repeated friction and duplicated accounts), passwords plus email verification (rejected: reset load and credential-stuffing risk), and full KYC at sign-up (rejected: blocks casual users who only want to learn or browse).

## ADR-012: Feature-based subscriptions governed by oxinov.com

**Date:** 2026-09-24. **Status:** Proposed (research). Oxinov uses one plan ladder (Free, Plus, Pro, Business, Enterprise) across all products, with **Oxinov One** as the cross-product bundle and product-specific plans only where a product has a distinct buyer. Marketplaces also earn transaction commission and promotion fees. The platform control plane owns the plan catalogue, subscriptions, entitlement keys, usage limits, metering, and billing; products check entitlement keys and remaining limits, never plan names. `oxinov.com/pricing` and `app.oxinov.com/billing` are the governing places to subscribe; mobile apps use Google Play Billing or Apple In-App Purchase for in-app digital subscriptions where store rules require it, and all channels unlock the same entitlements everywhere. Nepal billing starts with prepaid periods through Khalti and eSewa. Details are in the [subscription model](../company/SUBSCRIPTION-MODEL.md).

Consequences: the control plane needs a plan and entitlement catalogue, usage metering, app-store receipt verification, and a subscription ledger before paid plans launch. Alternatives considered: separate subscriptions per product app (rejected: fragmented billing and repeated charges for the same person) and plan-name checks inside products (rejected: every pricing change would need product releases).

## ADR-013: Expand Agri Market into Oxinov Commodity Market

**Date:** 2026-09-24. **Status:** Accepted in principle; subject to the product release gate and legal review. The adopted agricultural marketplace concept is expanded into **Oxinov Commodity Market** at `market.oxinov.com` (alias `commodity.oxinov.com`), covering agricultural produce, industrial raw materials and construction commodities, commercial machinery, and circular second-hand equipment and vehicles. The [Agri Market charter](../products/AGRI-MARKET.md) is superseded by the [Commodity Market charter](../products/COMMODITY-MARKET.md).

Choice: one product plane (`market-web`, `market-api`, `market-worker`, `database/products/market`) with category-specific rules rather than separate agricultural, industrial, and re-commerce products. High-value transactions use a milestone escrow workflow recorded in the platform payments ledger; funds are held and settled only through licensed bank escrow or settlement accounts and payment providers, never as an Oxinov stored-value balance. Condition grading, inspection partners, and vehicle ownership-transfer checks gate escrow release.

Consequences: the platform must provide escrow-state ledger entries, payout adapters, and dispute tooling before this product launches; the policy set gains the Marketplace Seller Policy, an Inspector Partner Agreement, and an escrow section in the payments policy; threat modeling and privacy must cover vehicle ownership documents and inspection reports. Second-hand motor vehicles and heavy machinery require Department of Transport Management compliance and legal review before launch, and categories can be enabled one at a time. Alternatives considered: keeping an agriculture-only marketplace (rejected: smaller addressable market and duplicate effort when equipment and raw-material trade share the same trust problems) and separate products per category (rejected: repeated seller onboarding, KYC, escrow, and dispute systems).

## ADR-014: Bedrock-first governed AI platform

**Date:** 2026-09-24. **Status:** Accepted as the target architecture; implementation remains gated. Oxinov will place one provider-neutral AI gateway in the shared platform boundary and use Amazon Bedrock first for generative AI, Guardrails, evaluated prompts, and approved RAG. Applications use model aliases and typed gateway contracts; web/mobile clients never call providers directly. Authorization and tenant/product filters run before retrieval and every tool call. Prompts, guardrails, retrievers, model versions, evaluations, budgets, and kill switches are controlled release artifacts. Standard logs and SOC events contain safe metadata rather than raw prompts or responses.

Amazon SageMaker AI is added only for validated custom training, predictive/vision/time-series models, or MLOps needs, and AWS IoT Greengrass may deploy approved models at the edge. Oxinov will not train a foundation model initially. The first pilots are a staff knowledge assistant and instructor-reviewed LMS authoring drafts; there are no state-changing model tools in the initial release.

Consequences: AI work depends on the platform backend, named owners, an approved data inventory, representative evaluation sets, language-specific review, quotas/budgets, and incident operations. Cross-Region inference requires a recorded processing-region decision. Alternatives considered: direct provider SDKs in each product (rejected: inconsistent authorization, safety, cost, and audit), SageMaker-first LLM hosting (rejected: unnecessary first-release operating burden), and immediate fine-tuning or foundation-model training (rejected: no evidence that prompts and RAG are insufficient).

## ADR-015: Rename OxinovLMS to Oxinov Edu

**Date:** 2026-09-24. **Status:** Accepted. The first product's customer-facing name is **Oxinov Edu**, served at `edu.oxinov.com`. This replaces the working name OxinovLMS and the planned address `lms.oxinov.com`, which was never launched. Internal technical identifiers keep the `lms` prefix: package names (`@oxinov/lms-api`, `@oxinov/lms-web`), folders (`lms-web`, `lms-api`, `lms-worker`, `database/products/lms`), database names (`oxinov_lms`), entitlement keys and design tokens (`lms.*`, `color.product.lms`), and requirement-ID ranges. Renaming them would be a risky code, migration, and data change with no customer benefit.

Consequences: DNS records, the OIDC client, redirect URIs, and TLS certificates use `edu.oxinov.com` when they are created; no existing deployment needs migration. Documentation uses "Oxinov Edu" for the product and keeps `lms` only in technical identifiers. Alternatives considered: "Oxinov LMS" and "Oxinov Learn".

## ADR-016: Keycloak sign-in implementation for ADR-011

**Date:** 2026-09-24. **Status:** Accepted (owner decisions of 2026-09-24); implemented locally in `devops/keycloak/`. Keycloak (26.7.x, pinned by digest; patch releases within the minor the extension is built for) at `id.oxinov.com` implements ADR-011 as follows. Email one-time codes use the community `for-keycloak/email-otp-authenticator` extension, pinned to the build for our Keycloak minor version and configured for six digits, a 10-minute expiry, and single use; its source is security-reviewed before production, and a small in-house authenticator replaces it if the review fails. The browser flow is Cookie, then Identity Provider Redirector, then a forms sub-flow of Username Form and Email OTP Form, with no password executor anywhere. Google is the first identity provider with Trust Email and forced sync; Google accounts whose email is not verified are refused with guidance to use an email code (FR-ID-2201). When a Google sign-in matches an existing Oxinov account by email, the first-broker-login flow links it only after the person confirms by an emailed link (Verify Existing Account By Email); silent automatic linking is not used. Staff use a separate `oxinov-staff` realm without self-registration and with mandatory passkeys or OTP (FR-ID-2209). Code-sending is rate-limited per email and per source at the edge, and realm brute-force detection is on.

Consequences: a Java extension enters the identity deployment and must be upgraded with Keycloak; linking needs one email round trip; the platform API trusts only verified-email tokens for activation (FR-ID-2205). Alternatives considered: building our own authenticator first (slower; kept as fallback), launching Google-only (excludes people without Google accounts), and automatic linking (Keycloak warns against it and has an open defect).

## ADR-017: Starter single-server hosting for the Oxinov Edu launch

**Date:** 2026-09-26. **Status:** Accepted; its Docker Compose runtime is superseded by k3s on the same server under ADR-018 the same day (owner decision of 2026-09-26: "Starter", about US$25–45 a month). Until paying schools depend on Oxinov Edu, production runs on one EC2 server (`t3a.medium`, 4 GiB, Mumbai) managed by `devops/terraform/environments/production/starter`, instead of the ADR-009 baseline of ECS Fargate, RDS, and ElastiCache (about US$150–250 a month). Docker Compose (`devops/starter/`) runs PostgreSQL 18, Keycloak at `id.oxinov.com`, the Edu and platform APIs, `edu.oxinov.com` and `app.oxinov.com`, and Caddy, which is the only service with open ports (80 and 443) and obtains Let's Encrypt certificates. The server has no SSH: administrators use Systems Manager Session Manager, and the Keycloak administration console and master realm return 404 publicly. Containers use the instance role (IMDSv2, hop limit 2), so no AWS access keys exist: lesson media live in a private, versioned S3 bucket with signed URLs, and sign-in emails go through a small SMTP-to-SES relay (`backend/workers/mail-relay`) that accepts only `no-reply@oxinov.com`. Application secrets are generated on the server into Parameter Store SecureStrings on the first deploy, never in Terraform state or GitHub. Recovery: nightly `pg_dumpall` to S3 (30 days), daily encrypted disk snapshots (7 days), CloudWatch recover and reboot actions, and daily automatic security updates. Releases are built, scanned with Trivy, and pushed to immutable ECR tags by `.github/workflows/deploy-production.yml`, which runs the deploy script over Systems Manager with a keyless OIDC role.

Consequences: one server is a single point of failure (a host fault means minutes of downtime; losing the disk means restoring the latest snapshot or dump, up to 24 hours of data); there is no WAF or CDN in front of the apps yet; capacity is limited to early schools. Move to the ADR-009 layout when a paying school needs an availability commitment, sustained load exceeds the server, or data volume makes restores slow; the images, migrations, and settings carry over unchanged. Alternatives considered: Lightsail (cheaper, but no instance roles, so long-lived keys), the full ADR-009 stack now (cost before revenue), and SES SMTP credentials (long-lived keys instead of the relay).

## ADR-018: Kubernetes (k3s) runtime and continuous deployment for every Oxinov service

**Date:** 2026-09-26. **Status:** Accepted (owner decisions of 2026-09-26: every push to `main` that passes CI goes to production automatically; Kubernetes with Helm; Terraform for every AWS resource; bash automation for every stage; optimize time and cost; "option 1 with k3s", total AWS spend within US$50 a month). Supersedes the Docker Compose runtime of ADR-017 (the server, backups, and security model stay) and the ECS Fargate runtime target of ADR-009.

- **Runtime:** one k3s node (certified Kubernetes with bundled Traefik, local-path storage, and a network-policy controller) on the existing `t3a.medium` (4 GiB plus 2 GiB swap), about US$40 a month with no control-plane or load-balancer fees. `devops/kubernetes/scripts/bootstrap-node.sh` installs pinned k3s and Helm (verified by SHA-256), configures Traefik (HTTP to HTTPS, Let's Encrypt through its built-in ACME resolver), turns off metrics-server, encrypts Secrets at rest, renders the application Secret from Parameter Store, and refreshes the ECR pull secret every 6 hours with the instance role. It is idempotent and runs before every release, so a rebuilt server converges without SSH.
- **Packaging:** one shared Helm chart (`devops/kubernetes/helm/oxinov`); each service is a `services:` entry with its own image tag, PostgreSQL is a StatefulSet on the encrypted disk, the nightly backup is a CronJob, and migrations are a hook that runs before every upgrade. Pods run non-root with numeric IDs, read-only root filesystems where possible, no capabilities, and deny-by-default network policies; only the pods that call AWS (Edu API, mail relay, backup) can reach the instance metadata service. `values-production.yaml` sizes it for the 4 GiB node (one replica each). The chart is published to ECR as an OCI artifact with every release.
- **Delivery:** trunk-based; `main` is always releasable. When CI succeeds for a push to `main`, `.github/workflows/deploy-production.yml` starts on its own. `devops/scripts/release-plan.sh` compares the commit with the running release and rebuilds only images whose inputs changed (documentation-only pushes deploy nothing; an API change never restarts Keycloak or PostgreSQL). Images are scanned with Trivy (HIGH and CRITICAL with a fix fail the release; upstream exceptions live in a reviewed, expiring `.trivyignore` next to the image) and pushed to immutable ECR tags. The node runs `helm upgrade --rollback-on-failure --wait` (Helm 4), then checks the public names through Traefik; a public smoke test follows. A failure at any step restores the previous release automatically. `devops/scripts/oxctl` wraps daily operations; `devops/scripts/check-delivery.sh` runs every delivery check locally and in CI.
- **Infrastructure and CI:** Terraform owns every AWS resource (including the budget); Dependabot opens grouped weekly updates for npm, GitHub Actions, base images, and Terraform. CodeQL and dependency review need GitHub Advanced Security on this private repository and wait for that decision.
- **Releases per product:** one `oxinov` release while Edu is the only product; the per-plane split of ADR-019 (a `platform` release plus one per product, each in its own namespace) happens with the second product, when it pays for itself.

Consequences: no human deploy step; a red `main` blocks releases; migrations must stay backward compatible with the previous image (expand, then contract) because rollback swaps images only; one node means ADR-017's availability limits apply until the roadmap's scale triggers move the chart, images, and scripts to Amazon EKS with RDS; memory is tight, so resource limits are part of every change; the team builds Kubernetes skills that carry over to EKS. Alternatives considered: staying on Compose (cheapest, but no path to the shared multi-service platform the owner chose), a `t3a.large` for k3s (about US$70 a month, over the budget; about US$50 with a one-year Savings Plan commitment), EKS now (more than US$150 a month before revenue), GitOps with Argo CD (a second controller on a small node; it arrives with EKS), and manual approval before production (the owner chose full automation; automatic promotion from staging arrives in the roadmap).

## ADR-019: Multi-product platform architecture (one company, many services)

**Date:** 2026-09-26. **Status:** Accepted (owner request of 2026-09-26); delivered in steps by the [DevOps roadmap](../devops/ROADMAP.md#multi-product-architecture-track). Builds on ADR-008 (platform and product planes), ADR-011 (one account), and ADR-018 (Kubernetes delivery). As Oxinov adds products (Edu now; Market, Jobs, Services next), every product must be independently releasable, isolated in failure, cost, and data, and cheap to add.

1. **One Helm release and namespace per plane.** A `platform` release (Keycloak, PostgreSQL, mail relay, account portal, platform API) and one release per product (`edu`, later `market`, …), each in its own Kubernetes namespace with resource quotas and network policies, all from the shared chart. A failed release rolls back only its own product, and products release on their own schedule.
2. **One service catalog.** `services.yaml` at the repository root is the single source of truth for every service: product, image and build target, build inputs, port, host, owner, and resource size. The release planner, CI, the chart values, and the documentation read it; `oxctl new-service <product> <name>` scaffolds the folders and the catalog entry (golden path). No service is registered by hand in several places. *Implemented 2026-09-26: see the [service catalog](../engineering/SERVICE-CATALOG.md); `oxctl new-service` scaffolds services.*
3. **Events between products, not direct calls.** Services write events to an outbox table in their own database in the same transaction, and a relay publishes them to Amazon SNS topics with an SQS queue per consumer (at-least-once, idempotent consumers, dead-letter queues). First events: `account.created`, `entitlement.changed`, `tenant.member.joined`. Synchronous calls stay for queries that need an immediate answer, through versioned APIs only.
4. **Feature flags.** Server-side flags per tenant, plan, or percentage, stored in the platform database behind the OpenFeature API so a hosted provider can replace it later. Deploying code (every push, NFR-17) is separate from releasing a feature; flags are removed once a feature is fully on.
5. **Shared observability.** OpenTelemetry tracing and metrics added once to `@oxinov/server-kit` and the web apps, propagating a trace ID across portal, APIs, and sign-in; one dashboard, service level, and error-rate alert per product.
6. **Contracts and ownership.** Versioned OpenAPI per API with a backward-compatibility check in CI and generated clients; `CODEOWNERS` per service; a written service level per product.
7. **Cost and data isolation.** Cost-allocation tags per product on AWS resources and namespaces, reported monthly. Each product keeps its own database and role today; regulated products (Market escrow and KYC) get their own database instance and, when they launch, their own AWS account.
8. **Modular monolith per product.** Each product stays one API until a measured scaling, security, or ownership need justifies extracting a service (YAGNI).

Consequences: more releases and namespaces to operate (automated by the catalog and scripts); events add eventual consistency and need idempotent handlers; a small amount of platform work lands before the second product. Alternatives considered: one release for everything (simplest, but one bad change rolls back the whole company), a service mesh (too heavy for one node), and a message broker such as Kafka or RabbitMQ (always-on cost and operations; SNS/SQS costs cents at this scale).

## ADR-020: English-only product and company language

**Date:** 2026-09-26. **Status:** Accepted (owner decision: "my company will only the english language … they can use the translator"). Every text Oxinov writes is in English only: websites, product interfaces, emails and notifications, policies, help, marketing, and support. Readers who prefer another language use their browser's or device's built-in translation, so pages must never block it (`lang="en"`, `translate="no"` only on brand names and code) and all copy follows the plain-English rules in the [brand voice](../design/BRAND.md#voice). Course content is separate: teachers and learners may write lessons, questions, and answers in any language and script, and the platform keeps full Unicode and right-to-left support for that content (NFR-08, FR-LANG-902). Locale settings that are not language (currency, time zone, date and number formats) still follow the reader.

Consequences: one set of copy and no translation cost or per-language pages; faster releases; smaller websites (Latin fonts only in the interface). Machine translation can misread idioms or legal nuance, so policies state that the English text is the binding version, and copy is written for translation. Replaces the "English and Nepali at launch" plan in FR-SITE-2101, FR-POLICY-2401, the policy framework, and the UI guidelines. Alternatives considered: native translations per market (costly to write and keep in sync, and slower to release), and English plus one local language (favors one country over a global audience).

## ADR-021: Production baseline until scale-out (media, cache, secrets, environments, monitoring)

**Date:** 2026-09-26. **Status:** Accepted (records decisions already built under ADR-017 and ADR-018 and the owner's US$50 budget; owner request of 2026-09-26 to align all documents with reality). Supersedes, for the starter phase only, the Mux, Redis/ElastiCache, Secrets Manager, staging, and production Prometheus choices in ADR-004, ADR-009, and the [technology stacks](TECH-STACK.md). The current picture is kept in [CURRENT-STATE.md](CURRENT-STATE.md).

1. **Lesson media on private S3, no video platform.** Uploads and playback use short-lived presigned URLs from `lms-api`; files play as uploaded. Mux (or AWS Elemental MediaConvert to HLS with CloudFront signed URLs) arrives when learners on slow connections need adaptive streaming or protected paid video, measured by playback failures and rebuffering (NFR-02).
2. **No Redis until a measured need.** Nothing in production needs a cache, queue, or fanout yet. The first need chooses between SQS (pay per use, fits ADR-019 events) and a Redis-compatible cache; Redis never holds records of truth.
3. **Secrets in SSM Parameter Store SecureStrings,** generated on the server and rendered into an encrypted Kubernetes Secret. Secrets Manager is used only where automatic rotation is required (for example RDS credentials at scale).
4. **No staging environment.** Delivery changes are rehearsed on a throwaway local k3s with the production versions (`rehearse-local.sh`), and every release is health-checked, smoke-tested, and rolled back automatically (NFR-17). Staging and preview environments with automatic promotion arrive in [DevOps roadmap](../devops/ROADMAP.md) Phase 4, when a second developer joins or the first school pays.
5. **Production monitoring through CloudWatch alarms, Kubernetes health checks, and the release smoke test.** The Prometheus, Alertmanager, and Grafana configuration (ADR-004) stays version-controlled and checked in CI, and runs locally; production metrics and traces arrive through OpenTelemetry (ADR-019 step 5) with a hosted or right-sized backend.
6. **AWS security services by trigger:** a CloudTrail trail with S3 retention and GuardDuty are the first additions (small monthly cost, owner approval); AWS Config, Security Hub, WAF, and a SIEM follow paying customers or regulated data ([security roadmap](../security/SECURITY.md#roadmap)).

Consequences: lower cost and fewer moving parts now; video is not adaptive, and there is no pre-production environment with real data shapes, so releases rely on tests, rehearsal, and automatic rollback; each item has a stated trigger and moves without changing application contracts. Alternatives considered: adopting the full target stack now (several times the budget) and dropping the target designs from the documents (they remain the plan for scale).

## ADR-022: Oxinov Jobs approved, and every product shares one Kubernetes node

**Date:** 2026-09-27. **Status:** Accepted (owner decisions of 2026-09-27: "full approval now", "full first release", and "do not increase the cost … all product and service has to use the same resources … if possible decrease the cost"). Builds on ADR-008, ADR-010, ADR-017, ADR-018, ADR-019, and ADR-021. Amazon EKS stays the scale-out design but is **not** adopted: its control plane alone (about US$73 a month) exceeds the budget.

1. **Jobs is approved** for the full first release in the [Jobs FRD](../requirements/JOBS-FRD.md) (FR-JOB-6001 to 6092), with the founder as product owner. It is built as a product plane (`jobs-web`, `jobs-api`, database `oxinov_jobs`) and deployed like every service, but `jobs.oxinov.com` is published only after Nepal counsel reviews the content and retention rules and the remaining items in its [product record](../products/jobs/README.md#release-gate) close. Where platform capabilities are missing, Jobs uses documented interim paths: operator verification instead of organization KYC, email through the mail relay instead of the notification service, and application-scoped messages until platform messaging exists.
2. **One node, one chart, one database server for every product.** All products run on the existing `t3a.medium` k3s node from the shared Helm chart, behind the one Traefik, with one Keycloak and one PostgreSQL instance holding a separate database and roles per product. A new product adds workloads, not infrastructure, and so adds no AWS cost.
3. **Kubernetes arbitrates the shared node:**
   - **Priority classes**, from the chart:
     - `oxinov-critical`: PostgreSQL, Keycloak, and the mail relay. Without them nobody can sign in, and data is at risk.
     - `oxinov-core`: live products and the platform (`edu-*`, `platform-*`).
     - `oxinov-growth`: products in development or early launch (Jobs).
   - **What priority does:** when the node runs short, the scheduler preempts lower classes to place higher ones, and the kubelet evicts pods that exceed their requests, lower priority first. Sign-in and Edu therefore survive a spike in Jobs.
   - **Honest sizing:** every workload declares measured requests and a memory limit.
   - **A memory budget checked in CI:** `scripts/service_catalog.py --check` fails when the production memory requests of all workloads exceed the node's allocatable budget (3.3 GiB of the 4 GiB, leaving room for k3s, Traefik, and the page cache).
   - **Growth path:** new products start in `oxinov-growth` with one replica and move to `oxinov-core` at launch. Horizontal autoscaling is not used on a single node, because extra replicas cannot add capacity there; it arrives with a second node.
4. **Scale-out stays trigger-based and cost-approved.** A second node, RDS, or EKS happens only when the memory budget can no longer hold the live products or an availability commitment requires it, and only with the owner's approval of the new monthly cost ([DevOps roadmap](../devops/ROADMAP.md)). The same chart and catalog move unchanged.
5. **Cost reduction instead of increase:** the largest lever is a 1-year Compute Savings Plan for the node (about a quarter off its on-demand price, with no upfront payment). It is proposed to the owner in [cost optimization](../devops/COST-OPTIMIZATION.md) because it is a commitment. Adding products never raises spend under this decision.

Consequences: products compete for 4 GiB, so every new workload must be small and measured; one node means shared failure (ADR-017), which is acceptable before paying customers; the memory budget makes crowding visible in CI instead of in production. Alternatives considered: EKS now (about US$150–200 a month, rejected by the owner), a second EC2 node or bigger instance (more cost), and separate clusters per product (more cost and operations).
