# Architecture decision records

Record each decision with date, status, context, choice, consequences, and alternatives considered. Do not silently change the stack in the FRD.

## ADR-001: PostgreSQL as system of record

**Date:** 2026-09-24. **Status:** Accepted. Use PostgreSQL for transactional platform and LMS data. PostgreSQL runs in Docker for local development and CI; production uses Amazon RDS for PostgreSQL with encryption, backups, isolated data subnets, and Multi-AZ according to the environment availability target. Default to shared tenant-scoped LMS tables with RLS and API authorization; offer a dedicated database only for a justified customer tier. Redis and object storage are supporting systems.

## ADR-002: Separate frontend and backend

**Status:** Proposed. Next.js renders web UI; NestJS owns APIs and business rules used by web and mobile. Separate Docker targets support independent builds and scaling.

## ADR-003: One shared mobile app

**Status:** Proposed. A single Expo app lets users switch their tenant workspaces and renders tenant branding. Separately branded binaries require a future decision because they multiply store releases.

## ADR-004: Prometheus and Grafana observability baseline

**Date:** 2026-09-23. **Status:** Accepted for the initial implementation. Services expose Prometheus-compatible metrics only on the private network. Prometheus stores short-term metrics and evaluates version-controlled rules; Alertmanager routes alerts; Grafana loads data sources and dashboards from version-controlled provisioning files. PostgreSQL and Redis use dedicated exporters. Do not use tenant IDs, user IDs, email addresses, URLs with identifiers, or other unbounded values as metric labels. Production may replace these containers with compatible managed services while preserving metric names, dashboards, and alert behavior.

## ADR-005: Separate security operations pipeline

**Date:** 2026-09-24. **Status:** Accepted as the baseline design. Operational metrics remain in Prometheus/Grafana. Security events follow the versioned schema under `security/soc/` and are sent to an access-controlled SIEM. OpenSearch Security Analytics with portable Sigma rules is the initial SIEM recommendation; a compatible managed SIEM may replace it. Amazon GuardDuty Runtime Monitoring supplies initial ECS Fargate runtime detections. Falco or GuardDuty may cover later EKS/EC2 workloads. Wazuh is optional when endpoint/host agents, file-integrity monitoring, inventory, or compliance capabilities justify the additional platform. Actual incident evidence is never stored in Git.

## ADR-006: Tenant context through transaction-local settings and a non-bypass role

**Date:** 2026-09-24. **Status:** Accepted for the first backend slice. The API connects as `oxinov_app` (no superuser, no `BYPASSRLS`, no DDL, no delete on audit history). Every data operation runs inside one transaction that first calls `set_config('app.tenant_id' | 'app.user_id' | 'app.auth_subject', value, true)`; row-level security policies compare rows to those settings and match nothing when they are absent. Tenant-owned tables also use composite `(tenant_id, id)` foreign keys so cross-tenant references are rejected by constraints. Consequences: every query needs a short transaction (acceptable at current scale; revisit with PgBouncer transaction pooling, which is compatible), and each new table must add its policy and grants in the same migration. Alternatives considered: per-request `SET ROLE` per tenant (role explosion), schema-per-tenant (migration fan-out), application checks only (single point of failure).

## ADR-007: Identity token verification and local development tokens

**Date:** 2026-09-24. **Status:** Accepted. The API verifies bearer tokens against an approved OIDC provider's JWKS (`AUTH_ISSUER`, `AUTH_JWKS_URL`, optional `AUTH_AUDIENCE`) without depending on a provider SDK. Only the subject, `email`, and `email_verified` claims are used by the current LMS slice; tenant roles always come from PostgreSQL. The provider client must supply the required verified-email claims before tenant creation can succeed. For local work and tests, HS256 tokens with issuer `oxinov-dev` are accepted when `AUTH_DEV_JWT_SECRET` is set; configuration refuses that secret unless `DEPLOY_ENVIRONMENT` is `local` or `ci` (amended 2026-09-24 after review: staging was previously allowed). Staging and production also require `AUTH_AUDIENCE`, so a token issued for another Oxinov product is rejected (FR-ID-2207).

## ADR-008: Shared company control plane with independent product planes

**Date:** 2026-09-24. **Status:** Accepted as the target architecture. `oxinov.com` provides the public company presence, `app.oxinov.com` provides one account and product launcher, and an OIDC identity service provides single sign on. The control plane owns organizations, product catalogue, plans, entitlements, shared billing records, audit, privacy, and support access. Oxinov Edu and every later product own their product workflows, deployments, and data and integrate through versioned APIs and events. Begin with modular applications and a transactional outbox; extract services or introduce a message platform only for measured scale, availability, security, data, or team-ownership needs. Keycloak is the default OIDC implementation while the application contract remains provider-neutral. Existing Oxinov Edu code is migrated incrementally rather than rewritten.

## ADR-009: AWS as the production cloud

**Date:** 2026-09-24. **Status:** Accepted. AWS is the production cloud, with `ap-south-1` Mumbai as the primary region subject to pre-launch Nepal network latency verification. Use separate accounts and VPCs for production and non-production, at least two Availability Zones for production, CloudFront/WAF and an Application Load Balancer at the public edge, ECS Fargate for initial Docker workloads, RDS PostgreSQL, ElastiCache, S3, ECR, Route 53, Secrets Manager/KMS, and Terraform. Store encrypted recovery copies in `ap-south-2` Hyderabad initially; add warm or active multi-region compute only when recovery objectives justify its cost. Amazon EKS remains a later option based on measured scale or team ownership. Alternatives considered were Google Cloud Delhi/Mumbai, which may offer strong Nepal latency, and Azure; AWS was selected for the overall networking, managed-service, security, and container ecosystem required by the product portfolio.

## ADR-010: Adopt Flo Softwares marketplace concepts as Oxinov product planes

**Date:** 2026-09-24. **Status:** Accepted in principle; each product remains subject to its release gate. The Flo Softwares organization contains three marketplace concepts: an agricultural commodity marketplace (KrishiConnect / BT-Bazz Commodity Market), an HR and jobs platform, and the Kaji service marketplace, plus a BT-Bazz OIDC authentication concept. They become three Oxinov product planes: Oxinov Commodity Market (`market.oxinov.com`, originally drafted as Oxinov Agri Market; see ADR-013), Oxinov Jobs (`jobs.oxinov.com`), and Oxinov Services Market (`services.oxinov.com`), each with a charter under `docs/products/`.

Choice: rebuild each product on the Oxinov stack (Next.js, NestJS, PostgreSQL with Prisma and row-level security, shared OIDC) rather than importing the Express applications. Source repositories are reference material for requirements, data models, screens, and business rules. Capabilities duplicated across the three concepts move to shared owners: identity, OTP, sessions, KYC, payments ledger, notifications, messaging, and file storage to the platform control plane; training, courses, exams, and certifications to Oxinov Edu. The BT-Bazz OIDC concept informs the Keycloak client and per-product role configuration but does not replace the ADR-008 identity decision.

Preconditions: Oxinov Pvt. Ltd. holds written rights to the Flo Softwares code, designs, and product names, including contributions by other developers; secrets committed to the source repositories are rotated before any content is reused; no stored-value wallet or customer-fund holding is built without Nepal Rastra Bank licensing review.

Consequences: the platform foundation must deliver shared KYC and payments before any of the three products launches, and the products are delivered one at a time in the order Oxinov Commodity Market, Jobs, Services Market. Alternatives considered: running the existing Express applications behind the Oxinov domain (rejected: four separate logins, duplicated KYC and payments, no tenant isolation, and inconsistent security and observability), and keeping the products under a separate Flo Softwares brand (rejected: fragments the Oxinov identity and customer account).

## ADR-011: One Oxinov account with simple sign-in and progressive trust

**Date:** 2026-09-24. **Status:** Accepted. Customers sign in at `id.oxinov.com` with Continue with Google or an email one-time code; Continue with Apple is added before an iOS app ships; customer passwords are not offered. One Oxinov account works across every launched product through OIDC single sign-on, and first sign-in grants a free member entitlement to all launched products. Sign-in stays low-friction by deferring checks: a verified phone (T2), individual KYC (T3), or business KYC (T4), plus just-in-time acceptance of a product-role policy, are required only for actions that affect other people or move money. The platform control plane owns trust levels, policy acceptances, and KYC; products enforce the required level per action. Staff use separate identities with mandatory MFA. Details are in [identity and access](IDENTITY-AND-ACCESS.md) and [platform policies](../company/PLATFORM-POLICIES.md).

Consequences: the platform needs SMS verification, KYC review, and policy-version storage before any marketplace launches; Keycloak must be configured with Google brokering, verified-email-only linking, and an email one-time-code flow (an extension, if required, needs review under the dependency policy). This refines ADR-008: "explicit entitlements" remain, but the member entitlement is granted automatically. Alternatives considered: per-product sign-up (rejected: repeated friction and duplicated accounts), passwords plus email verification (rejected: reset load and credential-stuffing risk), and full KYC at sign-up (rejected: blocks casual users who only want to learn or browse).

## ADR-012: Feature-based subscriptions governed by oxinov.com

**Date:** 2026-09-24. **Status:** Proposed (research). Oxinov uses one plan ladder (Free, Plus, Pro, Business, Enterprise) across all products, with **Oxinov One** as the cross-product bundle and product-specific plans only where a product has a distinct buyer. Marketplaces also earn transaction commission and promotion fees. The platform control plane owns the plan catalogue, subscriptions, entitlement keys, usage limits, metering, and billing; products check entitlement keys and remaining limits, never plan names. `oxinov.com/pricing` and `app.oxinov.com/billing` are the governing places to subscribe; mobile apps use Google Play Billing or Apple In-App Purchase for in-app digital subscriptions where store rules require it, and all channels unlock the same entitlements everywhere. Nepal billing starts with prepaid periods through Khalti and eSewa. Details are in the [subscription model](../company/SUBSCRIPTION-MODEL.md).

Consequences: the control plane needs a plan and entitlement catalogue, usage metering, app-store receipt verification, and a subscription ledger before paid plans launch. Alternatives considered: separate subscriptions per product app (rejected: fragmented billing and repeated charges for the same person) and plan-name checks inside products (rejected: every pricing change would need product releases).

## ADR-013: Expand Agri Market into Oxinov Commodity Market

**Date:** 2026-09-24. **Status:** Accepted in principle; subject to the product release gate and legal review. The adopted agricultural marketplace concept is expanded into **Oxinov Commodity Market** at `market.oxinov.com` (alias `commodity.oxinov.com`), covering agricultural produce, industrial raw materials and construction commodities, commercial machinery, and circular second-hand equipment and vehicles. The [Agri Market charter](../products/AGRI-MARKET.md) is superseded by the [Commodity Market charter](../products/COMMODITY-MARKET.md).

Choice: one product plane (`market-web`, `market-api`, `market-worker`, `database/products/market`) with category-specific rules rather than separate agricultural, industrial, and re-commerce products. High-value transactions use a milestone escrow workflow recorded in the platform payments ledger; funds are held and settled only through licensed bank escrow or settlement accounts and payment providers, never as an Oxinov stored-value balance. Condition grading, inspection partners, and vehicle ownership-transfer checks gate escrow release.

Consequences: the platform must provide escrow-state ledger entries, payout adapters, and dispute tooling before this product launches; the policy set gains the Marketplace Seller Policy, an Inspector Partner Agreement, and an escrow section in the payments policy; threat modeling and privacy must cover vehicle ownership documents and inspection reports. Second-hand motor vehicles and heavy machinery require Department of Transport Management compliance and legal review before launch, and categories can be enabled one at a time. Alternatives considered: keeping an agriculture-only marketplace (rejected: smaller addressable market and duplicate effort when equipment and raw-material trade share the same trust problems) and separate products per category (rejected: repeated seller onboarding, KYC, escrow, and dispute systems).

## ADR-014: Bedrock-first governed AI platform

**Date:** 2026-09-24. **Status:** Accepted as the target architecture; implementation remains gated. Oxinov will place one provider-neutral AI gateway in the shared platform boundary and use Amazon Bedrock first for generative AI, Guardrails, evaluated prompts, and approved RAG. Applications use model aliases and typed gateway contracts; web/mobile clients never call providers directly. Authorization and tenant/product filters run before retrieval and every tool call. Prompts, guardrails, retrievers, model versions, evaluations, budgets, and kill switches are controlled release artifacts. Standard logs and SOC events contain safe metadata rather than raw prompts or responses.

Amazon SageMaker AI is added only for validated custom training, predictive/vision/time-series models, or MLOps needs, and AWS IoT Greengrass may deploy approved models at the edge. Oxinov will not train a foundation model initially. The first pilots are a staff knowledge assistant and instructor-reviewed LMS authoring drafts; there are no state-changing model tools in the initial release.

Consequences: AI work depends on the platform backend, named owners, an approved data inventory, representative evaluation sets, language-specific review, quotas/budgets, and incident operations. Cross-Region inference requires a recorded processing-region decision. Alternatives considered: direct provider SDKs in each product (rejected: inconsistent authorization, safety, cost, and audit), SageMaker-first LLM hosting (rejected: unnecessary first-release operating burden), and immediate fine-tuning or foundation-model training (rejected: no evidence that prompts and RAG are insufficient).

## ADR-015: Rename OxinovLMS to Oxinov Edu

**Date:** 2026-09-24. **Status:** Accepted. The first product's customer-facing name is **Oxinov Edu**, served at `edu.oxinov.com`. This replaces the working name OxinovLMS and the planned address `lms.oxinov.com`, which was never launched. Internal technical identifiers keep the `lms` prefix: package names (`@oxinov/lms-api`, `@oxinov/lms-web`), folders (`lms-web`, `lms-api`, `lms-worker`, `database/products/lms`), database names (`oxinov_lms`), entitlement keys and design tokens (`lms.*`, `color.product.lms`), and requirement-ID ranges. Renaming them would be a risky code, migration, and data change with no customer benefit.

Consequences: DNS records, the OIDC client, redirect URIs, and TLS certificates use `edu.oxinov.com` when they are created; no existing deployment needs migration. Documentation uses "Oxinov Edu" for the product and keeps `lms` only in technical identifiers. Alternatives considered: "Oxinov LMS" and "Oxinov Learn".

## ADR-016: Keycloak sign-in implementation for ADR-011

**Date:** 2026-09-24. **Status:** Accepted (owner decisions of 2026-09-24). Keycloak (26.7.x, pinned by digest) at `id.oxinov.com` implements ADR-011 as follows. Email one-time codes use the community `for-keycloak/email-otp-authenticator` extension, pinned to the build for our Keycloak minor version and configured for six digits, a 10-minute expiry, and single use; its source is security-reviewed before production, and a small in-house authenticator replaces it if the review fails. The browser flow is Cookie, then Identity Provider Redirector, then a forms sub-flow of Username Form and Email OTP Form, with no password executor anywhere. Google is the first identity provider with Trust Email and forced sync; Google accounts whose email is not verified are refused with guidance to use an email code (FR-ID-2201). When a Google sign-in matches an existing Oxinov account by email, the first-broker-login flow links it only after the person confirms by an emailed link (Verify Existing Account By Email); silent automatic linking is not used. Staff use a separate `oxinov-staff` realm without self-registration and with mandatory passkeys or OTP (FR-ID-2209). Code-sending is rate-limited per email and per source at the edge, and realm brute-force detection is on.

Consequences: a Java extension enters the identity deployment and must be upgraded with Keycloak; linking needs one email round trip; the platform API trusts only verified-email tokens for activation (FR-ID-2205). Alternatives considered: building our own authenticator first (slower; kept as fallback), launching Google-only (excludes people without Google accounts), and automatic linking (Keycloak warns against it and has an open defect).
