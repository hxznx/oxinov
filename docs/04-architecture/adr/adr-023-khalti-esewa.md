# ADR-023: Oxinov sells its own courses first, with Khalti and eSewa

**Date:** 2026-09-27. **Status:** Accepted (owner decisions of 2026-09-27: "use Khalti and eSewa for payments" and, for whose merchant account receives the money, "Oxinov's own courses only"). Implements the payment-provider adapter of the [company architecture](../platform-architecture.md#payments) for Oxinov Edu (FR-CATALOG-303, FR-PAY-2701, FR-PAY-2702).

1. **Oxinov is the only seller for now.** Paid courses can be bought only from workspaces listed in the Helm value `payments.sellerTenantIds` (tenant UUIDs, never slugs, so nobody can claim a seller by picking an address). Payments go to Oxinov Pvt. Ltd.'s own Khalti and eSewa merchant accounts. Other schools stay free-course only; Oxinov never collects money on another school's behalf, so there are no payouts, commissions, or questions about holding funds for others. How schools sell (their own merchant keys, or Oxinov collecting and paying out) is decided later.
2. **Khalti ePayment and eSewa ePay v2, in NPR, one-time purchases.** The learner pays on the provider's site; Khalti is a redirect and eSewa a signed form (HMAC-SHA256 over `total_amount,transaction_uuid,product_code`). Only courses priced in NPR are sellable; Khalti needs at least Rs 10. Subscriptions, coupons, and refunds are later steps.
3. **Only the server's own check grants access.** Coming back from the provider proves nothing: the return page asks the Edu API to verify, and the API asks Khalti (lookup) or eSewa (status check) itself. Access is granted only for a completed payment of exactly the expected amount. Each provider transaction is recorded once in `provider_events`, a payment leaves PENDING once (conditional update), and one payment grants at most one entitlement (unique `payment_id`), so repeated, concurrent, or replayed checks cannot grant twice. Amount mismatches and reused transactions are refused and raise security events.
4. **Keys stay with the owner.** `KHALTI_SECRET_KEY`, `ESEWA_PRODUCT_CODE`, and `ESEWA_SECRET_KEY` are entered by the owner in Parameter Store and reach the API as optional Secret entries; a missing key switches that provider off. `payments.mode` is `sandbox` until live keys exist, and the published eSewa test merchant is refused in `live` mode.

Consequences: no revenue from other schools' courses yet; a learner who closes the browser before returning can still get access by opening the course's payment page again (the check is repeatable), but there is no background reconciliation job or provider webhook yet, so daily reconciliation (FR-PAY-2704) and refunds are manual until they are built. Alternatives considered: each school connecting its own merchant keys (more setup per school and per-school secrets), and Oxinov collecting for every school with monthly payouts (needs payout operations and a check of the rules on holding funds for others).
